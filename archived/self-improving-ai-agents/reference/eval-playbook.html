Eval playbook

How to build an evaluation for one real agent workflow, what each metric means, and the failure taxonomy to classify runs against.

Two printable pages · Companion to Lessons 12 and 13, and to Arc V

Build it in five steps

  • Choose one workflow and one decision. Not "evaluate our agents", but "should we switch the monthly-report agent to the fusion architecture?" An eval that cannot change a decision will not be maintained.
  • Collect 20 to 50 real tasks from actual traffic, deliberately over-weighting the cases that went wrong. Synthetic tasks measure a distribution nobody uses.
  • Define success as a judgement you would defend. Make it binary where possible, by asking whether you would have sent this and whether the number matched the source. Break anything subjective into yes-or-no criteria before scoring it.
  • Grade a baseline by hand. It is painful and it happens once, and it calibrates every automated judge you build afterwards. Thirty items is enough.
  • Keep the held-out set separate from the iteration set. You overfit everything you look at repeatedly, and you do it as much as the agent does.

Which metric answers which question

MetricDefinitionAnswersMisleads when
pass@1Succeeds on one attemptWhat a user sees todayYou quietly retry in production
pass@k / coverageSucceeds at least once in k attemptsIs the capability there at all?Reported as if it were product performance
pass^kSucceeds on all k attemptsCan this run unattended?Rarely, because this is the honest one, and it will look bad
Cost per solved taskTotal spend divided by successesIs the extra compute worth it?You ignore the cost of a wrong answer reaching someone
Steps to completionTool calls or turns usedIs it thrashing?It is used as a target, and shorter is not better if it fails
Recovery rateRuns that hit an error and still finished correctlyHow brittle is it?Errors are silently swallowed by tools

Report pass@1 and pass^k together. The first is optimistic and the second is pessimistic, and the distance between them states your reliability problem as a number. A workflow at 85 percent pass@1 and 40 percent pass^5 is not an 85 percent workflow.

Failure taxonomy, for classifying every bad run

Do not record that a run failed. Record which of these it was, because each one has a different fix.

ClassLooks likeFix in
Bad planSensible steps and a wrong decomposition, so it solves an adjacent problemLesson 8
Missing capabilityNo sampled attempt gets close, and coverage and pass@1 are both near zeroLessons 2 and 9
Bad selectionA good attempt existed and was discardedLessons 4 to 6
Tool failureWrong observation, silent empty result, unhelpful errorLesson 7
Error cascadeOne early mistake propagates and the agent never goes back to check itLesson 13

Spec gamingPasses every check, satisfies nobodyLesson 7, using held-out checks
Right for wrong reasonsCorrect output reached by an incoherent path, which recurs unpredictablyLesson 4, using process checks

Twenty classified failures tell you more than two hundred unclassified ones, because the distribution is your roadmap.

Traps

  • The judge is also your selector. If one component both picks outputs and grades them, your eval is measuring its own preferences, so keep them separate.
  • Benchmark contamination. Public benchmarks leak into training sets. Use them for orientation, never as evidence about your workload.
  • Averaging away the tail. A mean hides the hard slice where all the value and all the risk sit, so report results per difficulty bin.
  • One run per task. Agents are stochastic and a single run is a sample of size one, so use at least five.
  • Unpinned versions. A model updated underneath you invalidates every comparison, so pin versions and re-baseline deliberately.
  • Grading only the output. The trace tells you why and the output only tells you whether, so log thought, action, and observation separately.
  • No cost column. Accuracy without cost can neither justify nor refuse an architecture change.

The weekly loop

  • Sample ten real runs and classify each against the taxonomy, which takes fifteen minutes.
  • Pick the largest class and apply the matching dial from Tuning dials.
  • Re-run the eval set. Report pass@1, pass^k and cost per solved task.
  • Touch the held-out set only when deciding to ship, and never more than monthly.
