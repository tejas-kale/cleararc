Tuning dials

Every lever this course gives you over an agent, what it costs, and the symptom that should make you reach for it. They are ordered roughly by effort.

One printable page · Start at the top and stop when the numbers move

Diagnose first

Before turning anything, run the two-number test from Lesson 3. Take 20 to 30 real tasks with known outcomes, run each one 10 times, and record pass@1, meaning the first run succeeded, and coverage, meaning any run succeeded. Everything below branches on the result.

  • Coverage is much higher than pass@1. The answer is in there and you are discarding it, so go to Selection and do not buy a bigger model.
  • Coverage is close to pass@1 and both are low. This is a real capability or context problem, so go to Capability.
  • Coverage is close to pass@1, both are high, and production still feels worse. Your eval does not resemble production, so go to Measurement.
  • Results vary wildly across runs of the same task. This is a reliability problem, so measure pass^k and then go to Reliability.

Reliability, for when the same task gives different outcomes

  • Measure pass^k rather than pass@k. Run each task ten times and count how many succeeded every time, because that number predicts what unattended production feels like.
  • Lower the temperature only after checking coverage. It reduces variance and coverage together, and if your selector is good you want the diversity.
  • Add a gate rather than a retry. Retrying until checks pass teaches the agent to satisfy checks, so hold some back, as Lesson 7 argues.
  • Bound the horizon. Shorter runs with checkpoints beat one long run, because error cascading compounds, as Lesson 13 explains.
  • Freeze what varies. Pin model versions, seeds where available, and prompt templates before concluding a change helped.

Measurement, the dial that makes every other dial readable

  • Twenty real tasks beat two hundred synthetic ones. Draw them from actual traffic, including the failures that annoyed you.
  • Grade against a decision rather than a score. Asking whether you would have sent this to a stakeholder beats a rating out of ten that clusters at 7.
  • Keep a held-out set you never iterate against. Everything you look at, you overfit.
  • Report cost per solved task rather than accuracy alone. Every dial above spends money, and the frontier you care about is quality per unit of spend.
  • Re-run the two-number test after each change. If coverage and pass@1 both moved you changed capability, if only pass@1 moved you improved selection, and if neither moved you changed nothing no matter how it feels.

The order to try things

  • Measure, using the two-number test. Nothing below this line means anything without it.
  • Raise the thinking budget. Minutes of work.
  • Fix the tools' failure messages. Hours of work, often the largest single gain.
  • Generate n and fuse. One hour, almost always positive.
  • Add deterministic checks on the output, with some held back.
  • Build a rubric judge with binary criteria, calibrated on 30 to 50 labels.
  • Route by difficulty so the expensive path runs only where it is needed.
  • Stack critic, rank, and fuse layers on offline work.
  • Only now consider a bigger model everywhere, or a fine-tune.
